# 자동차 사고 과실비율 분석 서비스

사용자가 입력한 사고 정보를 **과실비율 인정기준(PDF)** 과 **한문철TV 사례 데이터**에 비교해, 과실비율과 근거가 담긴 **분석 보고서**를 만들어 주는 웹 서비스입니다. 담당자의 승인을 거쳐 결과가 사용자에게 공개됩니다.

> ⚠️ 본 서비스의 결과는 참고용이며 법적 효력이 없습니다. 실제 과실비율은 보험사 협의, 과실비율분쟁심의위원회, 법원 판단에 따라 달라질 수 있습니다.

---

## 1. 전체 서비스 흐름

1. 사용자가 사고 정보를 입력하고 **[사건 등록 및 분석]** 버튼을 누릅니다.
2. 사건이 DB와 구글시트(`사건목록`)에 등록되고, 웹 사고 목록에 **분석 진행중**으로 표시됩니다.
   - 시트 입력 항목: 사건번호, 사고 일시, 날씨, 사고 위치, 사고 경황 등
3. 새 사건이 등록되면 AI Agent가 데이터를 읽고 주요 내용을 정리합니다.
4. RAG로 PDF 2종과 한문철TV 데이터를 검색해 입력 내용과 비교하고 과실비율을 판단합니다.
5. **과실비율 분석 보고서**를 작성합니다. (판단기준, 근거, PDF 참조 페이지, 한문철TV 참조 내용 및 영상 URL 포함)
   - 개인정보는 비식별화하거나 제외하고, 당사자는 **사용자 A / 상대방 B**로 표기합니다.
   - 5-1. 정보가 부족해 분석할 수 없으면 상태를 **정보 보완 필요**(원 요구사항의 "분석 실패")로 바꾸고, **어떤 항목을 입력해야 하는지** 답글로 안내합니다. 사용자는 같은 사건 안에서 정보를 보완하고 **[저장 후 재분석]**을 누릅니다. (2-1절 참조)
6. 보고서가 완성되면 담당자에게 전달되고, 담당자는 **승인** 또는 **거절**을 선택합니다.
7. **승인** → Agent가 보고서를 바탕으로 사건 목록에 답글을 작성하고 상태가 **분석 완료**로 바뀝니다.
8. **거절** → 시트 데이터를 다시 읽어 분석을 재실행합니다. (최대 5회)
   - 8-1. 5회차까지 모두 거절되면 담당자가 거절 사유를 사건 목록에 직접 답글로 작성합니다.

## 2. 사건 상태

사용자 화면에 보이는 상태와 시스템 내부 상태를 구분합니다.

| 내부 상태 | 사용자 화면 표시 | 설명 | 다음 행동 |
|---|---|---|---|
| `RECEIVED` | 분석 진행중 | 접수 직후 | — |
| `ANALYZING` | 분석 진행중 | Agent 분석 중 (재분석 포함) | — |
| `NEEDS_INFO` | **정보 보완 필요** | 사고 정보가 부족해 기준을 적용할 수 없음 | 부족 항목 수정 → [저장 후 재분석] |
| `NEEDS_REVIEW` | **추가 검토 필요** | 정보는 있으나 적용할 기준을 특정하기 어려움 | 추가 증거·확인사항 안내 / 담당자 검토 |
| `ERROR` | **분석 중 오류 발생** | 서버 오류·시간 초과 등 시스템 문제 | 같은 정보로 다시 시도 |
| `PENDING_APPROVAL` | 분석 진행중 | 보고서 작성 완료, 담당자 승인 대기 | — |
| `COMPLETED` | 분석 완료 | 승인됨. Agent 답글 작성 | — |
| `MANUAL_REPLY` | 분석 진행중 | 5회 거절. 담당자 직접 답글 대기 | — |

모든 문제를 "분석 실패" 하나로 묶으면 사용자가 무엇을 해야 하는지 알 수 없으므로, 원인별로 상태와 다음 행동을 구분합니다.

```
RECEIVED → ANALYZING ─┬→ NEEDS_INFO   ──(정보 보완 → 저장 후 재분석)──→ ANALYZING
                      ├→ NEEDS_REVIEW ──(추가 자료/담당자 검토)────────→ ANALYZING
                      ├→ ERROR        ──(같은 정보로 재시도)──────────→ ANALYZING
                      └→ PENDING_APPROVAL ─┬→ 승인 → COMPLETED
                                           └→ 거절 → ANALYZING (거절 N/5)
                                                      └→ 5회차 거절 → MANUAL_REPLY → COMPLETED
```

### 2-1. 정보 보완·재분석 정책

**원칙: 한 사고는 하나의 사건으로 유지하고, 그 안에서 정보 보완과 재분석을 반복합니다.** 사건번호는 바뀌지 않습니다.

1. **2단계 검사**
   - ① 제출 시 **폼 검증**(규칙 기반, LLM 미사용): 사고장소 유형 미선택 같은 명백한 누락은 해당 항목 옆에 즉시 안내하고, **입력한 내용은 유지**합니다.
   - ② 접수 후 **Agent 충분성 검사**(의미 기반): "교차로 사고입니다"만으로는 신호 유무와 양측 진행 방향을 알 수 없는 경우처럼, 내용을 해석해야 알 수 있는 부족분을 찾습니다.
2. **구체적인 보완 안내**: 부족한 항목을 필드 단위로 알려 줍니다.
   > 과실비율 분석을 위해 추가 정보가 필요합니다. 교차로의 신호등 유무와 A·B의 진행 방향을 확인해 주세요. 기존에 입력한 내용은 저장되어 있습니다. **[수정 후 재분석]**
3. **바로 이어서 수정**: 결과 화면과 사건 목록 양쪽에 [수정 후 재분석] 버튼을 두고, 눌렀을 때 **기존 값이 채워진 수정 화면**에서 부족한 항목을 강조합니다. 저장 버튼은 [저장 후 재분석]으로 표시해 저장과 분석이 함께 진행됨을 알립니다.
4. **"모름" 선택지**: 사용자가 실제로 모르는 정보(신호 상태, 상대 차량 속도 등)는 **"모름"으로 답할 수 있게** 합니다. 추측으로 입력하게 하면 분석 신뢰도가 떨어집니다.
   - 항목을 **핵심 항목**(사고유형을 결정: 신호 상태, 진행 방향, 충돌 부위 등)과 **보조 항목**(수정요소에 영향: 속도, 날씨 등)으로 나눕니다.
   - 보조 항목이 "모름"이면 분석을 진행하되 보고서 `불확실성`에 명시합니다.
   - 핵심 항목이 "모름"이면 가능한 경우의 **조건부 분석**(예: "신호가 있었다면 …, 없었다면 …")으로 진행하거나 `NEEDS_REVIEW`로 보냅니다.
   - **"모름"으로 답한 항목은 다시 요구하지 않습니다.** (같은 질문 반복 방지)
5. **보완 전후 이력 보존**: 입력은 버전(`input_version`)으로 저장하고, 각 분석 결과는 어떤 입력 버전으로 만든 것인지 함께 보존합니다. 정보를 수정한 뒤 재분석하기 전에는 이전 결과에 **"수정 전 정보로 분석한 결과"**라고 표시합니다.
6. **횟수 규칙**
   - 담당자 **거절 횟수(최대 5회)**는 사건 단위로 누적합니다.
   - 사용자의 **수정 후 재분석**과 `ERROR` 재시도는 거절 횟수에 포함하지 않습니다. (남용 방지용 상한은 별도로 둘 수 있음)
7. **수정 가능 시점**: `ANALYZING` 중에는 수정 불가(진행 중 분석을 취소하거나 완료를 기다림), `PENDING_APPROVAL` 중에는 수정 시 현재 보고서를 폐기하고 재분석, `COMPLETED` 이후 수정은 새 입력 버전으로 재분석하되 **담당자 재승인**을 거칩니다.
8. **개인정보**: 보완 안내 답글에는 사용자가 입력한 개인정보를 그대로 되풀이하지 않고, 항목 이름만 안내합니다.

## 3. 기술 스택

| 영역 | 선택 | 비고 |
|---|---|---|
| 언어 | Python | |
| 프론트 | **Streamlit** (MVP) | 정식 서비스 단계에서 Next.js로 교체 검토. 프론트는 FastAPI만 호출하는 "화면 역할"로 제한 |
| 백엔드 | **FastAPI** | 사건 등록/조회, 승인·거절 API |
| Agent | **LangGraph + LangChain** | 상태 머신 기반 분석 파이프라인 |
| DB / 벡터 | **Supabase (PostgreSQL + pgvector)** | 실제 처리용 원본 DB + RAG 벡터 저장 |
| 시트 | **Google Sheets API** (서비스 계정) | 사건 목록 기록·열람용 미러링 |
| 작업 큐 | FastAPI `BackgroundTasks` → **DB 작업 테이블(`jobs`)** | 안정화 단계에서 전환. Celery/Redis는 도입하지 않음 |
| 자동화 | 별도 도구 없음 (Dify 제외) | 알림은 FastAPI 코드에서 직접 호출 |
| 임베딩 | **OpenAI `text-embedding-3-large` (1536차원)** | 확정. 입력 8,191토큰이라 현재 청크를 그대로 사용, pgvector HNSW 한도(2,000차원)에 맞춰 1536으로 축소 |
| LLM | **미정** | 분석·요약용 모델 선정 필요 |

### 설계 원칙

- **DB가 원본, 구글시트는 미러링.** 시트는 담당자가 눈으로 확인하는 용도이며, 처리 로직은 DB 상태를 기준으로 합니다.
- **분석 파이프라인은 LangGraph로 단일화.** Dify 등 다른 워크플로우 도구와 역할이 겹치지 않게 합니다.
- **참조(PDF 페이지, 영상 URL)는 검색된 청크의 메타데이터에서만 가져옵니다.** LLM이 직접 페이지 번호나 URL을 쓰지 못하게 해서 환각을 막습니다.
- **개인정보 비식별화는 LLM 호출 전에** 수행합니다.

## 4. 구글시트 구조

DB가 원본이므로 시트는 아래 두 개를 단방향(DB → 시트)으로 동기화합니다.

**`사건목록`**: 사건번호, 접수일시, 사고일시, 날씨, 사고위치, 도로유형, 사고경황, 사용자 차량 진행방향/속도, 상대 차량 진행방향/속도, 신호상태, 블랙박스 여부, 상태, 입력버전, 거절횟수, 최종답글

**`분석이력`**: 사건번호, 회차, 입력버전, 결과유형(보고서/정보부족/검토필요/오류), 보고서(JSON), 담당자 결정, 거절사유, 일시

## 5. Agent 처리 파이프라인 (LangGraph)

```
[입력 정리] → [충분성 검사] ─ 부족 → [정보 보완 필요 처리: 보완 항목 안내]
                  │ 충분
                  ▼
           [개인정보 비식별화] → [사고유형 분류] → [RAG 검색]
                                                    │
                                                    ▼
        [과실비율 판단] → [보고서 생성(구조화 출력)] → [담당자 알림] → 승인/거절 대기
```

1. **충분성 검사**: 사고 유형, 진행 방향, 신호 상태, 충돌 부위 등 필수 항목 확인. 부족 시 `NEEDS_INFO`로 바꾸고, 화면이 해당 입력칸을 강조할 수 있도록 **필드 단위 목록**(`field`, `reason`, `question`)을 구조화해 반환합니다. "모름"으로 답한 항목은 다시 묻지 않습니다. 정보는 충분한데 기준을 특정하지 못하면(검색 결과 신뢰도 낮음 등) `NEEDS_REVIEW`로 분기합니다. 시스템 오류는 작업 재시도 후 `ERROR`로 처리합니다.
2. **비식별화**: 이름, 차량번호, 연락처, 정확한 주소 제거 후 "사용자 A / 상대방 B"로 치환
3. **사고유형 분류 → 검색**: 분류된 유형 코드로 PDF 청크를 먼저 정확히 찾고, 의미 검색으로 보완
4. **과실비율 판단**: PDF의 **기본 과실비율**에서 시작해 **수정요소(가감)**를 적용. 도로교통법 조문은 위반 근거 인용용, 한문철TV 유사 사례는 **참고 근거**로만 사용
5. **보고서 생성**: 스키마로 구조화 출력을 강제
6. **재분석**: 담당자의 거절 사유(선택 입력)를 다음 회차 힌트로 전달하고, 사유가 없으면 "이전 결과와 다른 근거를 재검토"하도록 지시. 모든 회차 결과는 `분석이력`에 보존

## 6. RAG 데이터

세 종류의 자료를 **용도가 다른 코퍼스**로 나누어 하나의 벡터 테이블에 적재하고, `corpus` 컬럼으로 구분합니다.

| corpus | 자료 | 역할 | 우선순위 |
|---|---|---|---|
| `common_2023` | 자동차사고 과실비율 인정기준 (2023.6.30) | **과실비율 판단의 1차 근거** (기본비율·수정요소) | 1 |
| `roundabout_2025` | 2차로형 회전교차로 비정형 기준 (2025.6) | 회전교차로 사고의 1차 근거 | 1 |
| `law_roadtraffic` | 도로교통법 (시행 2026.10.13) | 위반 여부·**법적 근거 조문 인용** (보조) | 2 |
| `hanmoonchul` | 한문철TV 영상 정보 (20,000건 수집) | 유사 사례·**참고 의견** (보조) | 3 |

> 과실비율은 항상 PDF 인정기준(1순위)에서 시작합니다. 도로교통법과 한문철TV는 근거를 보강하는 용도이며, 기본비율을 바꾸지 않습니다.

### 6-1. 인정기준 PDF 청크 (준비 완료)

| 자료 | 폴더 | 원본 | 청크 수 |
|---|---|---|---|
| 자동차사고 과실비율 인정기준 (2023.6.30) | `rag/common_rag/` | 600쪽 | 189개 (사고유형별 기준 163개) |
| 2차로형 회전교차로 사고 과실비율 비정형 기준 (2025.6) | `rag/roundabout_rag/` | 76쪽 | 17개 (사고유형 15개) |

각 폴더는 두 자료 모두 같은 구성이며, **서비스가 실제로 읽는 파일은 `chunks.jsonl` 하나**입니다. 폴더를 합치지 않고 그대로 둡니다.

| 파일 | 서비스 실행 시 사용 | 용도 |
|---|---|---|
| `chunks.jsonl` | ✅ | 벡터DB 적재용. 한 줄에 청크 하나 |
| `chunks/*.md` | ❌ | 사람이 내용 확인하는 용도 |
| `index.md` | ❌ | 유형코드 → 청크 파일 목차 |
| `build_chunks.py` | ❌ | 원본 PDF로 재생성할 때만 사용 (`pypdf`, `cryptography` 필요) |
| `README.md` | ❌ | 각 자료의 설명서 |

**메타데이터 (두 자료 공통 스키마)**

| 필드 | 설명 |
|---|---|
| `id` | 청크 ID. 회전교차로는 `roundabout_202506_` 접두사가 있고, 2023판은 접두사 없음 |
| `title` | 유형코드와 제목 |
| `codes` | 사고유형 코드 배열 (예: `["차43-2"]`, `["회전-6"]`). **정확 일치 필터**용 |
| `category` | 자동차-자동차 / 자동차-보행자 / 자동차-자전거 (총설 등 26개는 빈 값) |
| `doc_type` | 사고유형별 기준, 총설, 수정요소 해설, 적용범위·용어정의, 변경대비표, 발간사, 개정경과 |
| `section_path` | 목차 경로 |
| `pdf_pages` / `printed_pages` | PDF 쪽 번호 / 책 인쇄 쪽 번호. 보고서의 **PDF 참조 페이지**에 사용 |
| `source` | 문서명과 발행연월 |
| `text` | 문맥 헤더 + 본문. **이 필드를 임베딩** |
| `char_count` | text 길이 (최대 약 7,000자) |

**적재·검색 시 주의점**

- **변경대비표 제외**: 현행 기준으로만 답하려면 `doc_type != "변경대비표"`로 필터링합니다.
- **코드 필터 우선**: 사고유형이 분류되면 `codes` 정확 일치로 먼저 찾고, 의미 검색은 보완용으로 씁니다.
- **회전교차로 ↔ 수정요소 해설 연결**: 회전교차로 자료는 수정요소 해설을 2023년판 `제3편 제2장 3. 수정요소의 해설`에 위임합니다. `회전-N` 유형을 검색하면 `common_2023`의 `수정요소 해설` 청크도 함께 가져옵니다.
- **판례 비율 ≠ 기본비율**: 청크에 포함된 참고 판례의 개별 사건 비율을 기본 과실비율로 쓰면 안 됩니다.
- **쪽 번호 2종**: 2023년판은 인쇄 쪽 = PDF 쪽 − 1, 회전교차로 자료는 두 값이 같습니다. 보고서에는 두 값을 모두 표기합니다.
- **그림 정보 없음**: 사고 도표(그림)는 텍스트에 없으므로 `pdf_pages`를 표기해 원본 확인을 안내합니다.
- **판본 기준**: 2023판과 2025년 6월판 기준이며 이후 개정 여부는 반영되지 않았습니다. 운영 전 최신 판 확인이 필요합니다.

### 6-2. 도로교통법 (RAG 추가 완료 · 보조 근거)

| 항목 | 내용 |
|---|---|
| 파일 | `도로교통법_법률__제22067호__20261013_.pdf` (101쪽, 시행 2026.10.13) |
| 상태 | 텍스트 기반 PDF (OCR 불필요). 조문 단위 분할 가능 |

**사용하는 이유**: 인정기준은 "몇 대 몇"을 알려 주지만 "어떤 조문을 위반했는가"는 법 조문이 근거입니다. 보고서의 판단기준에 `도로교통법 제25조의2제2항(회전교차로 진입 시 양보)`처럼 조문을 인용하면 설득력이 높아집니다. 수정요소(서행불이행, 신호위반, 보행자 보호의무 위반 등)가 어느 조문에 해당하는지 연결하는 데에도 쓰입니다.

**사용 범위 (보조 코퍼스)**

- 과실비율 숫자는 법에서 나오지 않으므로 **비율 계산에는 사용하지 않고**, 위반 여부와 조문 인용에만 사용합니다.
- 사고 판단과 관련 있는 장(총칙, 보행자 통행방법, 차마 통행방법 등 제1~3장 중심)을 우선 적재하고, 벌칙·면허·행정처분 등은 제외하거나 낮은 우선순위로 둡니다.
- 인정기준 청크에 "관련 법규" 항목이 이미 있어 일부 겹치지만, 인정기준에는 없는 조문이나 최신 조문 문구를 확인하는 용도로 유효합니다.
- 이 PDF는 **법률만** 포함합니다. 시행령·시행규칙(예: 세부 기준)은 포함되어 있지 않습니다.

**청크 결과 (`rag/law_rag/`, 생성 완료)**: 조문 194개 → 청크 **212개** (목차·부칙·삭제 조문 22개 제외). 조(條) 하나가 청크 하나이고, 2,000자를 넘는 조문(제2조 정의, 제49조, 제82조, 제93조, 제148조의2, 제160조)만 항·호 경계에서 나눕니다. `priority`는 1~5장이 `high`(99개), 나머지가 `low`(113개)이며, 검색은 기본으로 `high`만 쓰고 필요할 때 `low`를 열어 둡니다. 생성 스크립트는 `rag/law_rag/build_chunks.py`입니다.

> 제외 기준은 **영상 종류(쇼츠 여부)나 글자 수가 아니라 "쓸 수 있는 내용이 있는가"**입니다. 쇼츠 설명은 짧아도 사고 상황 1~2줄과 한문철 변호사의 한 줄 의견이 들어 있어 분석에 쓸모가 큽니다.

- **타임스탬프 없음**: 자막이 없으므로 구간(타임스탬프) 정보는 만들 수 없습니다. 보고서 스키마의 `타임스탬프`는 선택 항목으로 두고, 영상 URL과 제목, 설명란 요약만 인용합니다.
- **비율의 출처 구분**: 설명란에는 ① 보험사 주장 비율, ② 시청자 투표 결과, ③ 한문철 변호사 의견이 섞여 있습니다. 보고서에서 오해가 없도록 `ratio_source`로 구분합니다.
- **설명 첫 줄의 숫자**(예: `108558`)는 사건 접수 번호로 보이며, 제목의 `28817회`는 회차 번호입니다. 둘 다 검색 대상에서는 제외합니다.
- **사고유형 연결**: 제목·설명에서 사고유형 키워드(회전교차로, 횡단보도, 차선변경, 후진, 우회전 등)를 LLM 또는 규칙으로 분류해 `related_codes`를 채우면 PDF 기준과 연결할 수 있습니다. 이 분류는 정제 단계에서 자동 처리하되 오류가 있을 수 있으므로 일부를 표본 검수합니다.
- **저작권**: 설명란 원문 전체를 그대로 보고서에 재배포하지 않고, **요약 + 제목 + URL 출처 표기** 중심으로 사용합니다.

### 6-4. 통합 적재 설계: `corpus` 컬럼

**목적**: 서로 다른 자료를 한 테이블에 넣되, 출처·우선순위별로 필터링하고 ID 충돌을 막습니다.

**`rag_chunks` 테이블 (Supabase / pgvector)**

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `pk` | bigserial, PK | 내부 키 |
| `corpus` | text, NOT NULL | `common_2023` / `roundabout_2025` / `law_roadtraffic` / `hanmoonchul` |
| `chunk_id` | text, NOT NULL | 원본 `id` (예: `0041_보31~보32`) |
| `title` | text | 제목 |
| `doc_type` | text | 사고유형별 기준, 총설, 법조문, 영상 등 |
| `category` | text | 자동차-자동차 등 |
| `codes` | text[] | 사고유형 코드 배열 (GIN 인덱스) |
| `section_path` | text[] | 목차 경로 |
| `pdf_pages` | text | PDF 쪽 번호 (PDF 코퍼스) |
| `printed_pages` | text | 인쇄 쪽 번호 (PDF 코퍼스) |
| `source` | text | 문서명과 발행연월 |
| `url` | text | 영상 URL (한문철TV) |
| `extra` | jsonb | 코퍼스별 추가 필드 (`law_article`, `ratio_mentions`, `video_id` 등) |
| `text` | text | 임베딩 대상 본문 |
| `embedding` | vector(N) | 임베딩 (N은 선택한 모델 차원) |
| `char_count` | int | 길이 |
| `created_at` | timestamptz | 적재 시각 |

```sql
-- 제약: 같은 corpus 안에서 chunk_id는 유일
ALTER TABLE rag_chunks ADD CONSTRAINT uq_corpus_chunk UNIQUE (corpus, chunk_id);

-- 인덱스
CREATE INDEX idx_chunks_corpus ON rag_chunks (corpus);
CREATE INDEX idx_chunks_codes  ON rag_chunks USING GIN (codes);
CREATE INDEX idx_chunks_doc_type ON rag_chunks (doc_type);
-- 벡터 인덱스 (HNSW 등)는 임베딩 모델 확정 후 생성
```

**적재 규칙**

| 폴더 / 파일 | `corpus` 값 | 비고 |
|---|---|---|
| `rag/common_rag/chunks.jsonl` | `common_2023` | `chunk_id`는 원본 `id` 그대로 |
| `rag/roundabout_rag/chunks.jsonl` | `roundabout_2025` | 〃 |
| 도로교통법 청크 | `law_roadtraffic` | 조문 번호는 `extra.law_article` |
| 한문철TV 정제 JSON | `hanmoonchul` | URL은 `url`, 비율 등은 `extra` |

**검색 전략 (corpus별 호출)**

| 단계 | 검색 대상 | 방법 |
|---|---|---|
| ① 1차 근거 | `common_2023` (+ 회전교차로 사고면 `roundabout_2025`) | `codes` 정확 일치 → 의미 검색 보완. `doc_type != '변경대비표'` |
| ② 수정요소 해설 | `common_2023` · `doc_type = '수정요소 해설'` | ①에서 찾은 유형의 수정요소 해설 추가 조회 |
| ③ 법조문 | `law_roadtraffic` | 사고 상황 키워드(신호, 양보, 보행자 보호 등)로 의미 검색, 상위 3~5개 |
| ④ 유사 사례 | `hanmoonchul` | `related_codes` 일치 우선 + 의미 검색, 상위 3~5개 |

보고서에는 각 코퍼스의 근거를 **섞지 않고 구분**해서 표기합니다. (PDF 근거 / 법 조문 / 한문철TV 참고 사례)

## 8-1. 환경변수와 Supabase 키

Supabase는 기존 `anon` / `service_role` 키를 2026년 말까지 폐기하고 새 키로 바꾸고 있습니다. 새 프로젝트는 새 키를 사용합니다.

| 환경변수 | 값 형태 | 대체 대상 | 용도 |
|---|---|---|---|
| `SUPABASE_URL` | `https://<project-ref>.supabase.co` | — | 공통 |
| `SUPABASE_PUBLISHABLE_KEY` | `sb_publishable_...` | `anon` | 공개용. **RLS 적용**. 현재 구조(Streamlit → FastAPI)에서는 미사용 |
| `SUPABASE_SECRET_KEY` | `sb_secret_...` | `service_role` | **서버 전용. RLS 우회.** FastAPI·적재 스크립트에서만 사용 |

- 모든 테이블이 RLS 활성화 + 정책 없음 상태이므로, publishable 키로는 데이터를 읽거나 쓸 수 없고 **secret 키로만** 접근됩니다.
- 화면(Streamlit) 코드에 secret 키를 넣지 않습니다. 키가 유출되면 Supabase 대시보드 `Settings > API Keys`에서 새 secret 키를 만들어 교체한 뒤 이전 키를 삭제합니다.
- `supabase` 파이썬 패키지는 최신 버전을 사용합니다. 구버전은 새 키 형식을 처리하지 못할 수 있습니다.
- 새 키를 만들어도 기존 legacy 키는 함께 동작하므로, 교체 중에도 서비스가 끊기지 않습니다.

## 9. 운영 시 유의사항

- **개인정보**: 입력 원문은 접근 권한을 제한하고, LLM·시트·보고서에는 비식별화된 내용만 전달합니다.
- **동시성**: 같은 사건이 중복 분석되지 않도록 상태 변경에 락 또는 멱등 처리를 둡니다.
- **재분석 상한**: 분석 횟수 5회에 도달하면 자동 재분석을 잠그고 담당자 답글 입력을 활성화합니다.
- **면책 문구**: 모든 보고서와 답글에 참고용·법적 효력 없음 문구를 포함합니다.
- **Supabase 무료 티어**: 일정 기간 미사용 시 프로젝트가 일시중지될 수 있어, 운영 단계에서는 유료 플랜 또는 점검 절차가 필요합니다.
